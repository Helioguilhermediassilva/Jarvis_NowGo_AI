## 1. Objetivo

Permitir convidar clientes externos (fora de `@nowgo.com.br`) para um cockpit
**zerado e isolado**, mantendo o cockpit interno NowGo intacto. O founder
(superadmin) navega entre cockpits via switch discreto no header, sem alterar
a identidade visual atual.

## 2. Decisões fechadas com o founder

A Fase 5.2 segue as 6 decisões registradas em `todo.md`: convite com seletor
explícito `internal/external`, 1 tenant por empresa cliente, isolamento total
de dados de negócio, convidado como `owner` do tenant criado, cockpit
totalmente zerado na criação, e navegação por switch no header somada à página
`/admin/tenants`. A identidade visual atual permanece **integralmente
preservada**.

## 4. Estado atual das queries

A maior parte dos endpoints `/api/brain/*` ainda chama uma função
`resolveInternalTenantId()` que devolve **sempre** o id do tenant `nowgo-ai`,
independentemente do usuário logado. Isso é exatamente o que precisa mudar.

Endpoints afetados pelo isolamento:

| Endpoint | Fonte | Tratamento atual | Tratamento alvo |
|---|---|---|---|
| `/api/brain/opportunities` | NowGoBrainRepository (Notion + PG shadow) | Usa `nowgo-ai` hardcoded | Receber `tenantId` da sessão V2 |
| `/api/brain/opportunities-via-repo` | idem | idem | idem |
| `/api/brain/deal-rooms` | PG | mistura de tenant + Notion | idem |
| `/api/brain/missions` | derivado | herdado | idem |
| `/api/financial/configs` e `/kpis` | PG | hardcoded | idem |
| `/api/users` | PG | hardcoded | filtrar por tenant ativo |
| `/api/df/*` | dataset estático | sem tenant | continua sem tenant (catálogo público) |
| `/api/jarvis/chat`, `/tts` | LLM | sem tenant | sem mudança |

Endpoints `auth/v2/*` já são tenant-aware via `requireV2Role(req, res, roles)`.

## 5. Conceito de "tenant ativo na sessão"

Hoje a sessão V2 (`sessions` table) já carrega `tenantId` único — a sessão
nasce vinculada ao tenant do usuário no momento do login. Para suportar
**switch entre tenants** sem invalidar a sessão, criamos um conceito separado:

- A **sessão** continua atrelada ao tenant primário do usuário (chamado
  *home tenant*) — usado para auditoria e segurança.
- Um **active tenant** opcional fica em um cookie HttpOnly secundário
  (`ng_v2_active_tenant`), validado a cada request contra `tenant_members`
  para garantir que o usuário tem permissão.
- Quando o `active tenant` é `null` ou ausente, o `home tenant` é usado.

Para o **superadmin** (você), as queries respeitam um privilégio especial:
o `active tenant` não precisa estar em `tenant_members`; a sessão pode
projetar-se em qualquer tenant (com auditoria).

Esse design tem três vantagens: (a) sessões antigas continuam válidas,
(b) o switch é instantâneo e seguro, (c) auditoria sempre sabe quem agiu
em qual tenant.

## 6. Modelo de fluxo: convite externo

```
                 [/admin/usuarios]
                        |
                  ▼ formulário
                  ┌──────────────────────┐
                  │ E-mail               │
                  │ Tipo: ◉ interno      │
                  │       ◯ externo      │
                  │ ── if externo ──     │
                  │ Empresa cliente: ___ │
                  │ Slug sugerido: ___   │
                  │ Role do convidado: ▼ │
                  └──────────────────────┘
                            │ POST /api/auth/v2/invite/create
                            ▼
                  ┌─────────────────────────────────┐
                  │ Backend (handler)               │
                  │  1. Valida role do chamador     │
                  │  2. Se mode=external:           │
                  │     a. cria novo `tenants`      │
                  │     b. role do convidado=owner  │
                  │     c. founder → superadmin     │
                  │        invisível (membership   │
                  │        oculta para esse tenant)│
                  │  3. Cria `invitations`         │
                  │     com tenantId destino        │
                  │  4. Envia e-mail via Resend     │
                  └─────────────────────────────────┘
```

Na aceitação (`/aceitar-convite/:token`), o handler já é tenant-aware: o
`invitations.tenant_id` é o destino correto — sem mudança nessa parte.

## 7. Plano de implementação (passos atômicos)

A implementação será feita em **5 commits incrementais**, cada um com testes
e deploy intermediário, sem quebrar nada do cockpit existente.

### Commit 1 — Backend: tenant ativo na sessão

- Adicionar `getActiveTenantId(req)` em `server/http/authMiddlewareV2.ts`.
- Adicionar mutation `POST /api/auth/v2/session/switch-tenant` que valida
  membership e seta o cookie `ng_v2_active_tenant` (HttpOnly).
- Adicionar query `GET /api/auth/v2/session/tenants` que devolve a lista de
  tenants visíveis ao usuário (para superadmin: todos; demais: do
  `tenant_members`).
- Vitest: 6 casos cobrindo membership válida, role superadmin, cookie inválido,
  troca para tenant inexistente, troca sem auth, projeção do home tenant.

### Commit 2 — Backend: aplicar tenant ativo nos endpoints de leitura

- Substituir `resolveInternalTenantId()` por
  `getActiveTenantId(req)` nos 6 endpoints listados na seção 4.
- Adicionar fallback explícito: se o usuário não tiver tenant ativo (ex.: GET
  via API sem cookie), responder 401 em vez de cair no `nowgo-ai`.
- Vitest: smoke test garantindo que sessão A não vê dados do tenant B.

### Commit 3 — Backend: convite com modo internal/external

- Estender `invite/create.ts` para aceitar `mode: "internal" | "external"`.
- Quando `mode === "external"`:
  1. Validar `clientCompanyName` e `tenantSlug` (slug único, kebab-case).
  2. Criar tenant em transação.
  3. Adicionar founder (chamador) como `superadmin` desse tenant via
     `tenant_members` com flag `hidden_for_clients = true` (para a UI do
     cliente não listar o NowGo como membro).
  4. Continuar com o convite normal apontando para o novo `tenantId`.
- Vitest: 5 casos (slug duplicado, tenant criado, role do convidado, founder
  como superadmin oculto, e-mail enviado com nome correto).

### Commit 4 — Frontend: AuthV2Context com active tenant + switch no header

- `useAuthV2()` passa a expor `activeTenant` e `availableTenants`.
- `AuthHeaderButtons` ganha um dropdown discreto entre "Cockpit Interno NowGo"
  e cada tenant cliente (visível apenas se `availableTenants.length > 1`).
- Quando o switch é acionado, dispara `POST /session/switch-tenant` e faz
  `invalidate` das queries de cockpit.
- Sem alterações em CSS dos componentes existentes; o dropdown reaproveita
  estilos `ng-header-*` existentes.
- Adicionar `/admin/tenants` listando todos os tenants do superadmin com
  contagem de membros, role e botão "Acessar como" → switch + redirect.

### Commit 5 — Frontend: AdminUsuarios com seletor internal/external

- Tela `/admin/usuarios` ganha radio button `Tipo: interno | externo`.
- Quando externo, aparecem 2 campos extras: nome da empresa cliente + slug.
- Tudo reutiliza estilos atuais (sem alteração visual).

## 8. Migrações de banco

A 5.2 não cria/altera tabelas. A única mudança no banco é adição de uma
**coluna opcional** em `tenant_members` para suportar a flag de membership
oculta:

```sql
ALTER TABLE nowgo_brain.tenant_members
  ADD COLUMN IF NOT EXISTS hidden_for_clients BOOLEAN NOT NULL DEFAULT FALSE;
```

Migração `0007_membership_hidden.sql`. Idempotente, segura, sem reescrever
linhas existentes.
